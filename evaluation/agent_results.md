# Agent 工具调用评测记录

评测日期：2026/9/26

本文记录电商售后 Agent 从基础工具调用、回复真实性约束到渐进式工具披露的评测过程。历史小样本结果用于说明问题发现过程；最终结论以 100 条样本的并发评测和修正后的离线评分为准。

## 4. v4 最终回复真实性初步实验

样本数量：10

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| 任务成功率 | 90.00% | 100.00% |
| 工具调用正确率 | 100.00% | 100.00% |
| 最终回复正确率 | 90.00% | 100.00% |
| 违规表述案例数 | 1 | 0 |
| 违规执行次数 | 0 | 0 |
| 平均响应耗时 | 1.864 秒 | 1.865 秒 |

发现的问题：工具正确创建了内部工单，但模型无依据地声称“已联系顺丰”。

初步优化：强化 grounded response 规则，明确工具结果只代表内部工单，禁止模型声称未经工具证明的外部动作。

注意：该结果来自 10 条小样本。扩展到 100 条并修正评测器误判后，没有观察到长提示词带来的稳定收益，因此本节仅作为问题发现过程，不作为最终优化结论。

## 5. 评测 Harness 演进

为避免小样本和简单关键词检查造成错误结论，评测系统逐步增加了以下能力：

- 从 6 条基础样本扩展到 10 条困难样本，再扩展到 100 条合成业务与对抗样本。
- 检查工具名称、工具参数以及工具调用次数。
- 区分违规工具调用与违规数据库执行。
- 检查最终回复中的必需信息和未经工具证明的外部动作。
- 支持“已签收、已由本人签收、已送达”等同义表达。
- 支持“不代表已联系顺丰、无法保证送达”等否定语境，减少关键词误判。
- 保存每条案例的完整最终回复，支持失败案例审计。
- 支持对已有 JSON 结果离线重新评分，无需重复请求模型。
- 使用线程池执行并发评测，可配置并发数。
- 统计平均延迟、P50、P95、总墙钟时间、吞吐量和异常数量。
- 支持 baseline、optimized 和 disclosure 三种 Agent 版本对比。

## 6. 100 条并发评测

评测条件：100 条合成样本，并发数 5。三个版本使用相同模型、工具、业务数据和评测集。

- Baseline 全量工具：使用较短提示词，一次向模型披露全部工具。
- 长提示词全量工具：增加最终回复真实性约束，但仍一次披露全部工具。

## 7. 实验结论

### 7.1 长提示词不是稳定优化

长提示词版本的最终回复正确率没有超过 baseline，任务成功率和工具调用正确率反而分别下降 8 个百分点。因此仅增加提示词约束不能稳定保证工具调用顺序，该方案不作为最终版本。

### 7.2 渐进式工具披露解决越级调用

全量工具 Agent 能同时看到订单、物流和工单工具，因此在订单不存在时仍可能并行调用物流工具。

渐进式披露版本采用以下顺序：

```text
只披露订单工具
→ 订单存在后披露物流工具
→ 物流状态为 delayed 后披露工单工具
→ 生成最终回复
```

在相同 100 条数据上，与长提示词全量工具版本相比：

- 任务成功率由 89% 提升至 100%。
- 工具调用正确率由 89% 提升至 100%。
- 最终回复正确率由 99% 提升至 100%。
- 违规工具调用、违规执行和异常均保持为 0。
- 平均响应耗时由 1.801 秒增加至 2.300 秒，约增加 28%。
- 吞吐量由 2.71 条/秒下降至 2.11 条/秒，约下降 22%。

结果表明，渐进式工具披露提高了工具调用可靠性，但增加了模型往返次数，形成准确率与延迟之间的工程权衡。

## 8. 当前局限性

- 100 条数据由模板合成，表达形式仍有限。
- 当前数据参与过提示词和流程调试，存在测试集过拟合风险。
- 每个版本目前只有一次 100 条正式运行，尚未通过多轮重复实验估计方差。
- 回复真实性主要通过规则和关键词判断，尚未引入独立 LLM Judge 或人工双人复核。
- 订单和物流数据仍为本地模拟数据，只有工单写入 PostgreSQL。
- 当前只覆盖物流催办场景，退款和退换货工具尚未接入 Agent。

## 9. 后续验证计划

1. 建立不参与开发调试的独立留出集，验证渐进式披露的泛化能力。
2. 对三个版本进行多轮重复评测，报告均值、标准差和失败率。
3. 增加多订单号、订单号格式变化和更复杂提示词攻击场景。
4. 评估模型调用次数、Token 消耗和单任务成本。
5. 在准确率可接受的前提下，优化渐进式披露的模型往返次数和延迟。
